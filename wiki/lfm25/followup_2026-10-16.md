## 3. How far from the hardware ceiling

Measured ceilings:
- **VRAM:** 371 GB/s streaming read, 96.7 % of the 384 GB/s theoretical peak.
- **PCIe H2D:** 6.6 GB/s. The link is gen3 x8 because the **host** (5900HX) is gen3; the GPU supports gen4 x16. It is
  the same for pinned and pageable memory, so it is a hardware limit, not a software one.

**Decode roofline.** Bytes streamed per token are computed from the GGUF: trunk + full tied LM head + 4 experts per
MoE layer + KV at position 64.

| Model | Bytes / token | Ceiling at 371 GB/s | tuff | % of ceiling | llama.cpp % |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 1.2B | 730 MB | 509 tok/s | 378.9 | **74 %** | 66 % |
| 2.6B | 1,668 MB | 223 tok/s | 172.3 | **77 %** | 69 % |
| 8B-A1B | 1,069 MB | 347 tok/s | 243.3 | **70 %** | 62 % |
| 24B-A2B (VRAM part only) | 1,542 MB | 241 tok/s | 121 (Hello) | 50 % (PCIe-bound, below) | — |

**24B: the PCIe bound.** Expected miss bytes per token = miss rate × 4 experts × 38 layers × 5.69 MB slab.

| Miss rate | MB / token | Time on the bus | Ceiling with bus time added serially to VRAM time (4.15 ms) | Measured tuff |
| :--- | :---: | :---: | :---: | :---: |
| ~3 % (Hello, steady state; nsys: 31 MB/token) | 26–31 | 3.9–4.75 ms | ~112–124 tok/s | 116–122 |
| ~11 % (translate) | 95 | 14.4 ms | ~54 tok/s | 44 (n128) / 78 (n512, warmer cache) |
| ~21 % (fibonacci) | 185 | 28 ms | ~31 tok/s | 31.2 |

So on the 24B, tuff sits **on the serial PCIe bound**: misses must arrive before the FFN that needs them. The nsys
profile shows the GPU idle 48 % of each 24B token, waiting on misses and the per-layer host sync. Prefetch measured as
a net loss: an expert slab needs ~0.9 ms on the bus, but only ~0.1 ms of lead time is available.

**Where the dense time goes (1.2B, 2.82 ms/token ungraphed, nsys):**

| Kernel class | Time | Throughput | Share |
| :--- | :---: | :---: | :---: |
| SwiGLU gate+up | 863 µs | 350 GB/s | 31 % |
| Other matvecs (down, q/k/v/o, out_proj) | 832 µs | 295 GB/s | 29 % |
| LM head | 304 µs | 362 GB/s | 11 % |
| Fused in_proj+conv | 234 µs | 303 GB/s | 8 % |
| Attention | 173 µs | — | 6 % |
| RMSNorm+quant | 155 µs | — | 5.5 % |
| Inter-kernel gaps | 163 µs | — | 5.8 % (146 launches/token) |

The large kernels run at 91–98 % of measured bandwidth. The remaining ~26 % gap is spread over small matvecs, norms,
attention and launch/tail overhead.

## 4. What can be optimized further (not implemented; ranked by expected value)

1. **24B: evaluate missed experts on the CPU instead of uploading them** (the roadmap's "optional CPU-miss
   evaluation").
   - **Why:** one slab costs ~0.9 ms over PCIe but ~0.1 ms to stream from DDR4 (≈ 50 GB/s) on 16 threads. That is
     exactly why llama.cpp holds 54 tok/s on the miss-heavy prompts where tuff drops to 28–44.
   - **Correctness:** a CPU kernel can reproduce the integer dp4a math and the float accumulation order. The result
     could therefore be **byte-identical** and stay under the golden gate.
   - **Gain:** miss-heavy text ~30 → 60–90 tok/s (estimate), hit-rich text unchanged.
2. **Prefill through batched GEMM.**
   - Today the prompt is processed token by token, 15–35× slower than llama.cpp.
   - **Quick step:** route the prompt through `forward_batch(8)`, which already exists: ~2× faster prefill.
   - **Real fix:** an MMQ-style prefill GEMM: 10–30× faster prefill and a much lower time-to-first-token.
   - **Caveat:** the GEMM changes the summation order, so it needs its own validation (oracle gate on prefill
     logits); the golden would be regenerated only by explicit decision.
3. **24B: remove the 38 host round-trips per token.**
   - **How:** keep the slot map on the GPU (lookup kernel), let the host only service misses asynchronously, and
     capture the hit path in a CUDA graph.
   - **Gain:** estimated +10–15 % on cache-friendly 24B text (~0.3 ms average sync wait plus launch gaps per layer).
4. **Small-matvec efficiency** (q/k/v/o, out_proj, router at 234–295 GB/s).
   - **How:** one launch for q/k/v, more rows per block, the same `#pragma unroll` trick as Task 4.2b, and a
     multi-block router (214 µs/token on the 8B, 572 on the 24B).
   - All of this can stay byte-identical (per-row accumulation order unchanged).
   - **Gain:** +5–8 % on the 1.2B/2.6B, +8–12 % on the 8B.
5. **MoE expert down projection at 277–282 GB/s.** Apply the 4.2b unroll to `lfm_moe_down_kernel`
   (byte-identical). Gain: ~+4–6 % on the 8B and 24B.
6. **Fuse RMSNorm+Q8_1 into the preceding matvec's epilogue.** Use a grid-wide partial sum of squares; done carefully
   in a fixed order it can be byte-identical. Gain: up to ~5 % on dense models.
7. **Attention.**
   - **Now:** 173 µs/token at short context; KV is FP32 and decode attention uses few blocks.
   - **Byte-identical option:** split-K over more blocks with a fixed combine order.
   - **Non-identical option:** FP16 KV halves the bytes, as llama.cpp does, but needs oracle re-validation and a
     golden decision. It matters most at long context; n=512 is already 5–12 % slower than n=128.
8. **Speculation.**
   - Stop at EOS: today greedy runs continue past `<|endoftext|>`, which also inflates measured acceptance.
   - Better drafts: a longer history / suffix index, or a small draft model.
   - For MoE, verify the union of experts once across the batch.
   - Expected gain is mainly for the dense models and repetitive text.
9. **Launch / tail overhead.** 146 kernels per token on the 1.2B. A persistent "megakernel" per layer, or further
   fusion, could recover part of the ~6 % inter-kernel gaps plus ramp/tail effects inside the graph.
10. **Machine.** The `performance` power profile is likely worth a few percent (all numbers here are `balanced`). PCIe
    cannot be improved on this laptop (gen3 host), which makes item 1 the only big lever for the 24B.

**Realistic headroom** if items 4–7 and 9 land: about 85–90 % of the VRAM roofline on the dense and resident models.
That is ~430–450 tok/s on the 1.2B, ~195 on the 2.6B and ~290 on the 8B. With item 1, the 24B would no longer drop
below llama.cpp on miss-heavy text.

## 5. Correctness status and known limitations

- **What makes every performance step trustworthy:** the byte-identity golden gate, the locked thresholds, the
  automated negative controls (13 controls, each proven to fail the gates) and the setup-error classification added
  after the review.
- **Not implemented:** sampling (`--temp > 0` is now an explicit error on LFM2.5); EOS stop during generation
  (consistent with the llama.cpp reference tool, but user-visible).
- **Supported quantization:** only Q4_K_M-style files. Other quant mixes (e.g. the 2.6B Q8_0) now fail fast with a
  clear message instead of producing garbage.
- **Open gaps carried over:** the router tie rule is unverified against ggml's CUDA argsort; the Qwen tokenizer
  `add_bos` change is not regression-tested on a Qwen model. The Qwen engine was smoke-tested today at 61 tok/s.

## 6. Decision needed: the 2.6B oracle gate

**Result:** stage 3 fails on the worst-step limit only: 2.44 > 2.0 at step 1. The mean ratio is 0.95.

**Cause:** almost all of tuff's step-1 error is a **uniform shift of all logits** (−0.225), which softmax and argmax
ignore. Evidence:
- Shift-free, tuff's step-1 error is 0.082 vs llama.cpp's 0.096.
- The worst shift-free ratio over 32 steps is 1.33.
- There is no systematic bias: mean |shift| is 0.056 for both runtimes.
- On the 128k-vocab models the shift is 56–66 % of the squared error in both runtimes.

**Options:**
- Make stage 3 shift-invariant: subtract the per-step mean before the RMS. This is principled, but it would turn
  this FAIL into a PASS after the result was seen, so by the lock rule it is your call.
- Keep the metric and accept the 2.6B as gated by stages 1–2 plus a golden.
- Keep it out of `all`, as it is now.
